# Треньки — заметки для Claude

Короткая шпаргалка по проекту. Полная документация — в README.md и докер/деплой-файлах.

## Стек
- Next.js 16 (App Router) + React 19, TypeScript, Tailwind 4.
- Prisma 6 + PostgreSQL. Миграции вручную в `prisma/migrations/<timestamp>_<name>/migration.sql`.
- Vitest для unit-тестов (`tests/lib/`).
- Деплой: Docker + nginx на reg.ru. Конфиги — `Dockerfile`, `docker-compose.production.yml`, `nginx.conf`.

## Auth
- Источник истины — **httpOnly cookie `trenki_session`** с JWT (HS256, библиотека `jose`).
- Логин только через email OTP: `POST /api/auth/email/send-code` → `POST /api/auth/email/verify-code` → ставит cookie.
- Все API-роуты получают `userId` через `requireAuthUser(request)` (`src/lib/coach/guards.ts`) или `getSessionUserId(request)` (`src/lib/auth-server.ts`). **Никогда** не доверять `telegramId`/`userId` из query/body/header.
- Логаут: `POST /api/auth/logout`. На клиенте — `clearAuth()` из `src/lib/auth.ts`.
- Админ-сессии (login+password) живут в БД (`AdminSession` модель), token в cookie — raw hex, в БД — `sha256(token)`. Хелперы — `src/lib/admin-session.ts`.
- Telegram-вход полностью отключён, все старые эндпоинты возвращают 410. Не возрождать без явной просьбы.

## Security headers
- CSP с nonce собирается в `src/middleware.ts` (только в production). Inline-скрипты должны получать `nonce={nonce}` из `headers().get('x-nonce')`.
- Статичные headers (HSTS, X-Frame-Options, Referrer-Policy, Permissions-Policy) дублируются в `next.config.ts` и `nginx.conf`.

## Логи
- Использовать `logger` из `src/lib/logger.ts` (JSON, уровни, PII-редактор для email/telegramId/password/code/token).
- Уровень — переменная `LOG_LEVEL` (default `info` в проде).
- ESLint предупреждает на `console.log` (allow `warn`/`error`).

## Тесты

Покрывают чистые библиотеки. БД не подключается — для интеграционных тестов нужна отдельная инфраструктура.

## Pose-данные (MediaPipe): сессии атлетов и эталоны тренеров
- Локальный прототип инвентаря — `/admin/pose/equipment` (ссылка в `/admin/pose`): тело + яркий мяч и две разные цветные метки клюшки. `equipment-tracker.ts` — HSV, связные компоненты, ограничения площади/формы и консервативная привязка объектов; текущие 2D-наблюдения, без предсказаний вместо потерянных точек. `useEquipmentTracking` читает тот же видеопоток, что `usePoseCamera`, в отдельном Worker до 15 Гц (fallback main до 10), кадр до 320 px по длинной стороне. Нет очереди; ответы/контуры старше 500 мс, скрытая вкладка, остановка и смена размеров/настроек очищают наблюдения и след. Линия клюшки только при двух видимых метках. Палитра или выбор цвета с исходного кадра; зеркальность фронтальной камеры и поля contain учитываются через `equipment-calibration.ts`. Перекрывающиеся цвета отклоняются. Камеру включают явно; выбор другой камеры сначала останавливает текущую. JSON-отчёт содержит настройки, координаты и параметры обработки без изображений/звука. Эталоны, оценка, API и БД не изменяются; это диагностический прототип, не оценка техники/3D/скорости. Физический iPhone ещё требует проверки.
- Быстрая разметка в `ReferenceViewer` / `SegmentTimeline`: «Начать отрезок» фиксирует начало по самому плееру, «Закончить отрезок» — конец (вместо прежнего добавления фиксированных 5 секунд). Открытая отметка показывается пунктиром и блокирует сохранение/прочие правки до завершения или «Отменить начало»; ошибочный конец сохраняет начало для коррекции. После завершения нужна «Сохранить разметку». Кнопки −5/+5 секунд читают актуальный `video.currentTime`, не зависят от частоты pose-кадров и ограничивают перемотку длиной эталона/видео (`reference-playback.ts`). Ручной ввод и перетаскивание сохранены.
- Границы рабочих отрезков в `SegmentTimeline` задаются перетаскиванием или вручную (минуты:секунды.миллисекунды либо секунды с точкой/запятой). Начало, конец и длительность выбранного отрезка видны постоянно и обновляются во время drag; стрелки меняют границу на 100 мс, Shift — на 1 с. «Ввести отрезок» создаёт новый диапазон, «Применить границы» меняет выбранный; затем нужна «Сохранить разметку». Пока ввод не применён/отменён, сохранение блокируется. `segment-editor.ts` отклоняет пересечения, выход за видео, длительность <500 мс и превышение 200 отрезков; сохраняет настройки оценки при переносе диапазона. Нормализация и API остаются совместимыми с существующими данными.
- Админский тест оценки — `/admin/pose/test` → `/admin/pose/test/[videoId]`, `LiveAssessment.tsx` + `usePoseCamera.ts`. Камера включается явно, lite/GPU→CPU, скелеты и оценка остаются в браузере; PoseSession и пользовательский прогресс не записываются. Оценщик — чистый `src/lib/pose/assessment.ts`: 3D-углы, явная перестановка сторон, синхронизация по времени видео с компенсацией времени inference/реакции. Только размеченные рабочие отрезки; пустая разметка запрещает запуск оценки, но не предпросмотр камеры. Запуск видео по нажатию не зависит от предварительного loadedmetadata. Нет видимых суставов — нет текущей оценки. Итог учитывает потерю камеры/частичную видимость; кадры с непригодным эталоном исключаются. При паузе, буферизации и скрытой вкладке оценка приостанавливается, перемотка сбрасывает результат; камера освобождается при завершении/выключении/уходе. Оценка экспериментальная, точность на реальных выполнениях ещё требует проверки.
- Настройки оценки хранятся в `segments[].assessment` (JSON, без новой миграции); старые отрезки используют профиль «Всё тело». Профили/валидация — `assessment-settings.ts`, редактор в `SegmentTimeline`. Разные соседние профили не склеиваются; пересекающиеся разные правила отклоняются. Сохранение из редактора проверяет `expectedUpdatedAt` под блокировкой Video; повторный анализ/авторазметка сбрасывают настройки. Перед запуском/возобновлением проверяются обязательные суставы и 3 секунды непрерывной видимости (`readiness.ts`); пользователь нажимает подготовку у телефона, тот же элемент видео разблокируется вызовом play/pause внутри нажатия, затем после свежего отсчёта тренировка начинается автоматически. Подготовку можно отменить; потеря камеры отменяет запуск, нативные controls не обходят проверку. Ошибка автоматического воспроизведения оставляет паузу и предлагает повторный запуск. Текущая оценка требует обязательных углов и ≥75% видимого веса, общий процент отображается только при ≥3 с распознанного выполнения, ≥75% покрытия оценки и пригодности эталона. Пропуски камеры/суставов/эталона показываются отдельно, слабое выполнение не считается недостатком данных. Эти пороги — экспериментальные, требуют проверки на реальных устройствах с тренером.
- Живое сравнение во времени — `temporal-assessment.ts`: одна задержка на окно 2,4 с, поиск ±300 мс вокруг ручного времени реакции (0–1500 мс реального времени, с пересчётом по playbackRate), только внутри того же рабочего отрезка и без будущих кадров. Набор сравниваемых суставов/вес эталона должен совпадать с фиксированным сравнением: пропуски не улучшают подстройку. Подстройка требует ≥8 пригодных наблюдений за ≥1,2 с, движения обеих поз и однозначного совпадения; неподвижность, разрыв, граница поиска/отрезка и плохая видимость оставляют фиксированное сравнение без процента темпа. Темп означает синхронность относительно времени реакции, не BPM; итог темпа требует ≥3 с распознанной синхронности и надёжного общего результата. `live-feedback.ts` сглаживает только отображение (не накопление), подсветка после ≥800 мс устойчивого расхождения, одна основная нейтральная подсказка без направленных рекомендаций.
- Камера использует `camera-detector.ts` → классический `scripts/pose-camera-worker.js` с OffscreenCanvas и передаваемым ImageBitmap, строго один кадр в обработке. Подготовка ассетов копирует закреплённый CJS SDK и Worker на наш домен. Нет поддержки Worker/ошибка инициализации — main-thread GPU→CPU; ошибка во время обработки сначала ставит тренировку на паузу, затем восстанавливает распознавание без автоматического возобновления. Снимок времени тренера берётся до асинхронного распознавания; после pause/seek/rate/buffering старые ответы отклоняются по версии, кадры старше 1 с не учитываются. Worker/bitmap/камера освобождаются при отмене и уходе. «Режим тренировки» фиксирует оба видео, оценку и управление в пределах viewport, смена ориентации/выход не пересоздают камеру; завершение возвращает полный результат.
- Звук в тесте включается явным нажатием (по умолчанию выключен, без сохранения между страницами). `useAssessmentAudio.ts` + `assessment-audio.ts`: Web Audio сигналы и ru-RU SpeechSynthesis, разблокировка в обработчике нажатия, тест громкости, запасные сигналы при отсутствии русского голоса. `audio-cues.ts` выдаёт отсчёт только по свежей готовности, объявляет фактический старт/паузу/завершение; потеря видимости и буферизация озвучиваются после выдержки, нейтральные подсказки — после устойчивого расхождения. Между разными подсказками ≥8 с, одинаковая не чаще 20 с; очередь речи не копится. Отмена, восстановление видимости, отдых, скрытая вкладка, mute и уход прерывают устаревшую озвучку; AudioContext закрывается. Проверка реальной слышимости и русского голоса на физическом iPhone ещё требуется.
- Запись кадров скелета — `PoseTracker.tsx` → `POST /api/pose-sessions`. Эталоны движений тренеров — `/admin/pose`: `PoseReferenceJob` → отдельный Docker-сервис `pose-worker` (`workers/pose-worker.ts`, Python MediaPipe heavy). Массовый запуск пропускает готовые эталоны; ручной анализ в браузере остаётся дополнительным способом.
- Фоновые результаты пишутся в отдельные закрытые объекты каждой попытки. Применение — транзакция с блокировкой Video и проверкой runToken, videoUrl и версии эталона; ту же блокировку должны брать все ручные записи/правки разметки эталона. Перезапуск воркера восстанавливается по heartbeat, ограничения CPU/RAM — в production compose. Шортсы в этой очереди не поддерживаются.
- Кадры — gzip-JSON в НАШЕМ S3 закрытым объектом (`pose/sessions/<id>.json.gz`, `pose/references/<videoId>.json.gz`, `src/lib/pose-storage.ts`). В БД — только `framesUrl` (`s3://…`) и сводка. Наружу кадры отдаёт только наш API после проверки доступа. До 22.09 кадры лежали в Cloudinary — перенос `/api/cron/pose-storage-migrate`.
- Доступ: атлет видит только свои сессии, тренер — только сессии атлетов своих команд со статусом ACTIVE (`src/lib/pose-access.ts` + `src/lib/coach/athlete-access.ts`); одной роли COACH недостаточно — это был IDOR. Оценку (PATCH) ставит только тренер команды атлета. На чтение `GET /api/pose-sessions/[id]` отдаёт ссылку на `/api/pose-sessions/[id]/frames` (та же проверка доступа, gzip из S3). Клиент распаковывает сам (`DecompressionStream('gzip')`).
- Совсем старые сессии лежат в `PoseSession.frames` (JSONB) — их тоже переносит `/api/cron/pose-storage-migrate`, до переноса работает legacy-ветка.
- Без `S3_*` env-переменных запись pose-сессий деградирует до старого JSONB-режима с warning'ом (эталоны — в `.pose-dev/`) — нормально для dev, в проде S3 должен быть настроен.

## Видео (S3 + серверная обработка)
- Новые видео и шортсы заливаются только файлом в наше S3 (`s3://uploads/…`), Kinescope для новых записей скрыт (решение владельца 16.09.2026). Старые Kinescope-записи читаются как раньше.
- При сохранении карточки создаётся `MediaJob`. Воркер `src/lib/media/worker.ts` (внутри процесса Next, будится из роутов и cron `check-workouts`) пережимает файл через ffmpeg и подменяет `videoUrl`. Правила сохранения карточки во время обработки — `src/lib/media/url-plan.ts` (покрыты тестами).
- Сырой исходник `s3://uploads/…` никогда не публикуется и не отдаётся атлетам. Не ставить `isPublished=true` строке с таким `videoUrl` в обход этих правил.

## Что НЕ делать без обсуждения
- Не возвращать Telegram-логин/виджет/QR (см. P0-ревью).
- Не возвращать чтение `telegramId`/`userId` из query/body — это IDOR.
- Не удалять deprecated-поля схемы (Profile.strength/endurance/... и Video.muscleGroupOld/*) без бэкфилла и тестов — там реальные данные пользователей.
- Не запускать `prisma migrate reset`/`prisma db push --accept-data-loss` на проде.
- Не возвращать pose-кадры в БД напрямую — только в S3 (решение владельца 22.09: pose-данные переехали из Cloudinary в S3).
